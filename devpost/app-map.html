Renewal Radar: App Map

A take-home guide to what was built. Snapshot of commit b2f9028 on 2026-10-23; the code can drift after this.

What it is

One static web page. A person picks Medi-Cal or CalFresh, enters the month on their last approval letter, answers one question, and sees a timeline of renewal and report dates, each with the official letter and quote behind it, plus a one-tap calendar file. Nothing is stored or sent.

Four small pieces do the work: the page shell and wiring (index.html, js/main.js), the pure date rules (js/rules.js) with their sources (js/sources.js), the renderer (js/render.js), and the calendar builder (js/ics.js). Tests in test/ run with Node's built-in runner and need no install.

A reference route through the code

Three stops. This route was prepared from the finished code, not toured interactively.

  1. The six-month rule. js/rules.js, nextNewAdult (around line 28) and the constant SIX_MONTH_START. A renewal on or after March 2027 is followed by one 6 months later; otherwise 12. That one comparison is the kernel of the whole app. mediCalSchedule walks it forward, drops past entries, and stops at the 18-month window.
  2. Where a date gets its source. Every entry carries ruleIds such as ['M2','M3']. js/render.js, whyThisDate, looks each id up in js/sources.js and builds the "Why this date?" disclosure. Nothing can appear on the page without an id, and a test refuses any id below high confidence.
  3. The payoff. js/ics.js, buildIcs, turns the same entries into an iCalendar file; js/main.js, downloadIcs, hands it to the browser as a download. test/ics.test.js parses the file back line by line.

To change this, start here

  • Wording on the page (labels, actions, the summary line): js/rules.js, inside mediCalSchedule and calFreshStandard. The checklist question lives in index.html.
  • A rule or its source: add or edit the row in research/FACTS.md first, mirror it in js/sources.js, then use its id in js/rules.js. The tests in test/rules.test.js and test/calfresh.test.js will tell you if a low-confidence id leaked.
  • How far ahead the timeline looks: WINDOW_MONTHS at the top of js/rules.js.
  • Colors and themes: the custom properties at the top of css/styles.css, one block each for light and dark.
  • Reminder timing: the alarms arrays on each entry's event in js/rules.js (-P7D is 7 days before, PT9H is 9 a.m. the same day).

A practice to reuse

Write the example before the rule, then let a test referee between them. The PRD recorded a plain example, "January 2026, Yes: January 2027, January 2028, July 2028" (devpost/prd.md, Medi-Cal New Adult Schedule). The spec later derived a tidy 18-month window rule. The test for that example (test/rules.test.js, "M8: January 2026 New Adult stays yearly once") failed on the first run: the window hid July 2028, the very renewal that shows the new six-month rhythm. The fix was one line in mediCalSchedule, recorded under Revisions in devpost/checklist.md. On another project: when an interview produces a concrete example, keep it verbatim as a test case. Derived rules written later should have to pass it, not the other way round.
